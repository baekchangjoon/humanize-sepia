# 기술 채널 적용

GitHub PR 본문·Jira 티켓·Confluence 해설서·구현 계획서·사내 기술 블로그를 쓰거나 다듬을 때 **이 파일 하나만** 읽는다. 공통 기준은 SKILL.md를 따른다. 다른 reference는 사용자가 해당 작업(자소서, 연구계획서, 대안 비교 등)을 요청할 때만 읽는다.

## 분량

- 사용자가 축약을 허용하거나 요청하면 중복·부연·자기평가("정직 기록", "핵심은 ~이다")·재요약 삭제를 필요한 수정으로 본다. **줄이는 대상은 이 네 가지뿐이다.** 아래 [의미 보호](#의미-보호) 문장은 줄이는 대상이 아니다.
- 분량 목표: 허용만 했으면 원문 이하, 비율을 지정했으면 그 비율(예: −30%)을 따른다.
- 축약체(`~함`·`~임`·명사 종결·괄호 부연)를 완결된 문장으로 풀 때는 같은 구간의 중복을 함께 덜어 분량이 원문을 넘지 않게 한다.
- 분량 목표는 의미 보호보다 아래다. 원문 이하를 맞추려면 의미 보호 문장을 지우거나 합쳐야 한다면 분량 목표를 포기하고, 줄이지 못한 이유를 한 줄로 보고한다.

## 보호 구간

다음은 표기까지 그대로 둔다. 위치·서식(목록↔표)은 바꿀 수 있다.

- 인라인 코드·코드 블록·경로·URL·커밋 해시·명령어·플래그
- REQ-ID·이슈 번호(`#123`, `ABC-123`)·버전·수치와 단위·비교 기준
- 체크박스(`- [ ]`)·상태 기호(🟢🟡🔴🔵)·추적 매트릭스
- 에이전트용 지시 블록(`> **For agentic workers:** …`, `REQUIRED SUB-SKILL`): 저장소에 남는 원본에서는 유지한다. Confluence 게시본처럼 사람이 읽는 사본이라고 사용자가 밝힌 경우에만 뺀다.

## 의미 보호

표기는 바꿀 수 있지만 **내용은 빠짐없이 남긴다.** 다른 문장과 합칠 때도 아래 요소가 결과에 그대로 읽혀야 한다.

- 결정의 근거: "~때문에", "~라서", "이유는", "근거는"으로 이어지는 왜
- 기존 결함·실패 조건: "~해도 통과했다", "~하면 깨진다", 고치기 전 상태 설명
- 주의·경고·부작용: "오히려", "단", "주의", "하지 말 것"
- 용어·기호 정의: "N은 ~", "~를 뜻한다", 약어 풀이
- 범위·대상 한정: "~만", "~에 한해", "이번 범위 밖", 대상 서비스·SUT 지정

점검: 원문에서 위 요소가 들어간 문장마다 결과의 대응 문장을 찾는다. 찾지 못하면 되살린다.

## 채널별 구조

| 채널 | 구조 | 말투 |
|---|---|---|
| GitHub PR 본문 | 요약(무엇·왜 1~3줄) → 변경 사항 → 검증(명령·결과 수치) → 리뷰 포인트·후속 | 한다체, 개조식 |
| Jira 티켓 | 배경 → 문제/요구 → 완료 조건(체크리스트) → 참고 링크 | 한다체, 개조식 |
| Confluence 해설서 | 결론 먼저 → 개념 설명(문단) → 예시·그림 → 한계 | 한다체, 설명은 문단 |
| 구현 계획서 | 목표 → 범위/비목표 → 제약 → 단계(체크박스) → 완료 기준 | 한다체, 개조식 |
| 사내 기술 블로그·회고 | 결론·요약 → 배경 → 과정 → 수치 결과 → 한계·다음 | 원문 종결체 유지(기본 한다체) |

- 원문에 이미 있는 섹션 순서는 독자 이해를 막을 때만 바꾼다.
- 표는 3열 이하·행 7개 이하일 때 목록보다 우선한다. 긴 설명이 들어가는 셀은 목록으로 푼다.

## 최종 점검

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check_preservation.py" <원문> <결과> [--max-ratio 1.0]
```

- 종료 코드 1이면 보고된 보호 토큰을 되살리거나 분량을 다시 줄인 뒤 한 번만 재검사한다.
- 서식 변경(표 분할, 코드 표기 분리)으로 생긴 오탐은 원문과 대조해 무시한다.
